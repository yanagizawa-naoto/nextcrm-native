# Administration UI: backup and restore preparation

Root integration: `NativeDataMaintenanceWindow(service:resources:onReviewActivation:)`, retain the instance, call `start()`, then present its `window`. For session switching, inject a `NativeDataMaintenanceController` with a thread-safe `sessionCheck` and use the controller initializer. `dismissForNavigation()` requests cancellation and waits for the task/cleanup before closing; `onClosed` signals that drain. `hasOperation` includes a file chooser. Root must drain this window before terminating or switching the application root.

`onPrepared` receives only the published destination URL and a typed backup/restore result after a fresh administration check. `onReviewActivation` is an explicit request to the separate activation workflow, not permission to activate. It is absent by default and no fake completion controls are displayed. The eight obligations remain “確認待ち”; users can select each row to read its resolution evidence. Root must revalidate authorization and all candidate manifests under its own activation fence.

The controller always runs fixed NativeBackup/NativeRestore APIs into a new private temporary container. A bounded second copy creates a private hidden sibling of the selected destination; it never replaces an existing target. It copies only the expected candidate files and managed directories, does not follow symlinks, verifies readback hashes, and uses same-filesystem RENAME_EXCL. Fresh authenticated admin and atomic publication are enclosed in the current database transaction. Each copy chunk and backend checkpoint checks authority; SQLite long-query cancellation checks refresh authority at most 100 ms apart. No callbacks expose partial data.

Cancellation before the commit seal wins and removes the attempt. Once the authorized commit seal is acquired, cancellation waits for its actual completion; a successful publication is reported as successful, never as cancelled. Commit failure rolls back the attempt’s newly published inode before exposing an artifact. Cleanup errors are surfaced rather than claimed successful. Previously existing destinations and the original backup remain untouched. Forced termination is covered by the separate private maintenance recovery journal. Controller records its two owned staging roots and publication intent; root App must call recoverStaging in a bounded background task to reclaim abandoned work. Unknown markers or changed identities remain pending.

Progress is coalesced in a lock-protected value and polled only while work or a page read is active. UI pages retain at most 100 rows. The reader streams and hashes each selected inventory, retaining only the requested page; no whole-job list or raw JSON is displayed. Existing result files are presented as recorded results, with revalidation required before activation. A failed authority check clears the result; every open, page read, reveal and activation-review handoff rechecks current authority.

Published file paths remain relative inside manifests. Backup source namespace is unchanged. Restore `stagingNamespaceSHA256` is updated to the published preparation folder’s crm.sqlite before export. That remains a preparation location, not the final activated namespace; root must calculate the actual final database path and bind keys then. No Keychain, external provider, runtime startup or root switch is invoked here. No clipboard API is used. Synthetic QA injects file panels/reveal callbacks and uses only its isolated SQLite/files. `native-data-maintenance-test.py --visible` additionally packages a unique QA app and checks the system save/open panels with actual CUA button actions; the default runner stays hidden. The explicit production source list is `NativeDataMaintenanceSources.json`, independent of pre-existing build outputs.

Foundation can canonicalize nonexistent /private/var paths differently after creation. Publication derives its preparation namespace from the already-existing canonical parent plus the new suffix, then verifies it again against the actual committed crm.sqlite before releasing the authorization fence. A mismatch rolls back the newly published directory; it never claims keys were relocated.
