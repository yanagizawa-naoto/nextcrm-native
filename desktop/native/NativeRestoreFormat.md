# Offline native restore staging, version 1

`NativeRestore.prepare(backupURL:schemaURL:sqlURL:destinationURL:)` accepts a completed NativeBackup v1 bundle and trusted current application schema resources. It creates only a new private directory below the resolved temporary directory. It never opens an existing application root, accesses Keychain, contacts a provider, rewrites jobs, or starts a runtime. The backup is read-only. A valid candidate contains `crm.sqlite`, the original managed file paths, `resume-plan.ndjson`, `files.ndjson`, `tables.ndjson`, `backup-snapshot.json`, and `restore.json`; a marker distinguishes staging from an activated application root.

The completed snapshot envelope is bounded to 4 MiB and strictly parsed. Database size/hash, manifest hashes, every declared table/schema/row count, current schema revision and CRM DDL, integrity/FK, every managed asset's size/hash, duplicate/unsafe paths and the complete DB-to-file inventory are checked. Metadata JSON lines are bounded to 64 KiB. SQLite disk indexes and 64 KiB copies avoid arrays of all jobs/files. Unknown native auxiliary tables and receipts remain byte-for-byte in the database. No `NativeDatabase` initializer runs in staging; isolated acceptance tests open the result through the actual initializer and verify all table values remain unchanged.

A private output is copied and checked before publication. Source files are reopened against pinned directory descriptors to detect replacement. Cancellation is checked per chunk/row and inside SQLite long queries. Failures remove only files created by that attempt. Files are independent inodes; native document files and avatar thumb/original files become 0400 and keep nlink=1. Missing originals/external references already declared pending by backup remain obligations, not silently repaired. Unsigned hash manifests prove internal consistency, not provenance or that a remote provider matches the snapshot.

`activationGate.phase = requiresActivationReview` applies to this staging result, not a permanent inability to restore. It carries the snapshot ID, database hash and source/target Keychain namespace fingerprints. Its machine-readable obligations name the responsible next step and resolution evidence; staging itself cannot produce that evidence. The later activation component must stop and drain every writer/listener/worker, hold an exclusive root-switch fence, reverify candidate hashes and revisions, bind credentials to the final root namespace (not this temporary path), reconcile jobs/receipts/relay state, then produce a separate explicit activation decision. It must not infer permission from `candidateCreated=true`, erase obligations or change all jobs to done/cancelled.

Resume-plan rows are streamed, not accumulated. Credential rows contain record identifiers/field/revision and storage scheme only, never secret values. Metadata entries contain keys and lengths, never settings values/tokens. Job rows retain IDs/state and classify active leases, delivery begun without receipt, known receipts, queued/local work and terminal receipts; original payload/result/MIME stay unchanged in SQLite. Unknown plugin state and event types require review rather than being guessed safe.

Source basis and resolution rules:

- NativeDatabase.claimJob reclaims expired running leases; runtime startup therefore remains suppressed until old processes are stopped and selected jobs are reconciled. Delivery timestamps and providerID receipts are preserved; existing review APIs can resolve individual outcomes after external evidence. SMTP unknown outcomes require explicit review, while smtpAccepted receipts must not cause another SMTP send (NativeMailSend/NativeDatabase).
- Invoice/campaign/report/task/project/order/lead sends retain frozen bodies, provider receipts and the original first-attempt time. Existing provider idempotency protection is time-limited (NativeDatabase.rearmJob/CRMInvoiceMail); restoring a past snapshot does not extend that period.
- NativePluginsRuntime fences lease/state after awaits. PluginData contains connector cursors, external IDs, locks/TTL claims and order references; compare provider state before enabling a connector. Never clear all plugin claims on restore.
- CampaignRelaySync and CalendlyRelaySync require unchanged instance/client binding and nondecreasing remote head. Preserve cursors, campaign registrations and event receipts; validate against the actual receiver before resuming. NativeMailSync similarly checks IMAP UIDVALIDITY, mailbox and endpoint before advancing a cursor.
- NativeAI/NativeMCP/NativePlugins/NativeMail/GoogleCalendar/Calendly credentials use DB-path-derived Keychain namespaces; invoice mail and campaign relay also have Keychain-only settings. Restore final-path namespace deliberately, verify each reference, and recover/re-enter rotated keys that no longer exist. Cleanup queues must remain disabled until this is complete. MCP signing URLs additionally depend on the original signing key/origin.
- User/password/session/API-token records and opaque Web ciphertext are retained but do not establish external credential availability. ImageUpload/legacy URLs may need a separate asset exporter. Snapshot provenance and final destination selection require an authorized operator.

Auxiliary table/index DDL is checked against `NativeRestoreSchema.swift`, generated from this source revision’s isolated real NativeDatabase initializer. The 92 CRM tables/indexes are checked against trusted schema.sql. Older or incompatible auxiliary DDL requires a separate explicit migration; staging does not repair it by silently running the initializer. Extra unknown tables remain preserved and require activation review.

The copied inventory manifests and original snapshot envelope carry hashes in restore.json so the later activation transaction can reverify without depending on the old backup location. For a restored asset, inventory `sourcePath` is its location in the new root; `archivePath` only identifies the original backup blob. Neither manifest grants activation permission. Google calendar `requestOutcome=confirmed`, SMTP `smtpAccepted=true`, and providerID receipts are recognized according to the existing workers; an unknown outcome remains a per-job review obligation.

## Preserved migration originals

M07 archive pairs are restored byte-for-byte under `native-credential-archives/` and appear as a `credentialArchive` review item. Restore keeps the source namespace binding; it does not make it active at the temporary destination. An explicitly admitted writable operation must verify hashes and rebind the nonsecret inventory to the final destination. `NativeCredentialMigrationArchiveReader` then rechecks current admission and exact binding before each original value is delivered for conversion. Read-only held workspaces are refused. No archive operation grants identity, provider, cleanup or worker-start authority, and unresolved non-credential holds remain in the inventory.
