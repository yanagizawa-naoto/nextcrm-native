# Native snapshot candidate (not restore)

This stage snapshots the entire native SQLite database and its **published, referenced managed files**. It opens only explicitly supplied fixture/application sources; tests use isolated synthetic data. It never reads/writes Keychain, starts workers, contacts providers, switches an application data root or overwrites an existing destination. A candidate is not a complete disaster-recovery package until its typed credential/namespace/job/activation obligations are resolved.

The integration boundary is `NativeBackup.prepare(source: NativeDatabase, destinationURL:)`. It always uses the supplied database’s `transaction` method; callers cannot substitute a no-op fence. `NativeDatabase.transaction` already uses an operation lock and `BEGIN IMMEDIATE` (NativeDatabase.swift:592). Under that fence, the backup reader establishes a separate read-only SQLite transaction and pins every managed file referenced by that snapshot. The fence is then released; the held read transaction is copied with incremental `sqlite3_backup`, while pinned files are streamed into independent candidate files. In WAL mode other writers can proceed during the bulk copy. DELETE journal mode may hold writers until the read snapshot ends. All application writers and file publication/reference cleanup must obey that transaction contract.

Document/PDF/mail pins are hard links to immutable inodes on the same filesystem and do not change the source bytes. A different-filesystem destination requires copying a referenced file while the fence is held, increasing the write pause; this is surfaced in result metrics/pending guidance. Lists/indexes must be disk-backed and reads bounded (64 KiB, SQLite backup page batches), with no open descriptor per asset or array of all files. Files absent or changed while being pinned/read, unsafe paths/symlinks, hash mismatches and cancellation abort the candidate. New private staging is removed on failure.

Known file boundaries:

Imported `migration.asset.v1.*` references are resolved against the current owner/model/field and source-value digest. Invoice PDFs and invoice attachments pin the matching managed path with its stored size/SHA256. Profile mappings additionally require the combined nullable avatar/image binding and respect the explicit clear marker; both thumbnail and exact original are required. Business columns and mapping JSON remain unchanged in SQLite. Stale mappings do not override edited fields; unhandled external references remain pending. Malformed/oversized mapping records and missing or corrupt required local files fail the snapshot. Document migration originals are already covered by their `migration-archive` object mappings.

- `native_document_objects.file_key` references all logical object mappings; unmapped `Documents.key` values under `native-documents/` preserve direct native files, including retained versions/deleted records. Published metadata carries size/SHA256. Documents/MCP PUT publishes under a DB transaction; cleanup reference checks are also transactional (CRMDocuments.swift, NativeMCPDocumentObjectStore.swift, NativeDocumentFiles.swift).
- `Invoices.pdfStorageKey` and applicable `Invoice_Attachments.storageKey` under `invoice-pdfs/` identify native PDFs. Rendering finishes before the transaction updates the reference, then the previous file is removed (CRMInvoicePDF.swift).
- `mail-outbox/<job UUID>.json` is required for nonterminal `native_outbox` rows with published `sha256`/`bytes` in payload or result. Invoice mail uses payload; task/project/order/lead/report/campaign workers use result. Bodies are created before publication and are immutable after the digest is recorded; terminal jobs may have deleted bodies. The exception is `campaigns/send-step` with `status=done` and `result.outcome=skipped`: an authorized campaign resume reuses the same job ID and published digest, so that body remains required and is backed up. Accepted/reviewed sends and explicitly cancelled recipients are not this resumable state. `native_mail_sends.mime` is a database BLOB and is included in the SQLite snapshot.
- `Users.avatar = native-avatar:v1:<UUID>.png` identifies `native-avatars/<UUID>.png`. The matching `<UUID>.original.{png|jpg|gif|webp}` (exactly one, ≤4 MiB) is also preserved. The avatar store publishes and updates Users transactionally and removes unreferenced files transactionally. Avatar pins use APFS clones or a bounded copy under the fence, never hard links, because the store requires nlink==1. Unknown legacy thumbnail-only data is preserved with a pending-original diagnostic; multiple originals or unsafe files fail. Pending PNGs and staging files are not referenced and are excluded.
- Plugin notification bodies created by NativePluginsMail are transient files without durable body references; they are excluded. Running plugin jobs and unknown external-send outcomes remain manual-review concerns after restore.

The snapshot must include every sqlite_master table, including native auxiliary tables, queue rows, metadata, audit, cleanup queues, cached content and job receipts. Source and candidate table/schema counts are compared; the candidate gets SQLite integrity and foreign-key checks. No application schema initialization runs on the source or snapshot. Extra metadata/file manifests live outside the source database. Known external document/PDF/avatar references are retained in the DB and reported pending, never fetched or silently claimed as backed-up bytes.

A source DB path-derived Keychain namespace is recorded as a fingerprint only. Secret values are not exported. Merely copying DB references does not preserve a key already deleted after rotation, move it to a new path/Mac, or make restored signing URLs valid. Restored jobs must remain stopped until external receipts, leases, idempotency state and relay cursors are reconciled. These remain typed pending scopes even when the local snapshot candidate passes all checks.

The copied database retains SQLite’s WAL-mode header when the source is WAL. The incremental backup contains the complete read snapshot in the main file, without a required WAL sidecar. Validation reopens this private, finished copy with SQLite `immutable=1` through its pinned descriptor; a subsequent application open can create its own WAL. No database-header bytes are patched. The backup API must be invoked outside an existing application transaction; restore activation is a separate gate. Legacy `ImageUpload` rows and unsupported document URLs are reported as external-file obligations.

A SQLite progress handler checks cancellation during long read/integrity queries, in addition to per-page and per-file chunk checkpoints. Logical-document mappings and frozen mail bodies require their published nonempty SHA256; direct legacy document files lacking a hash are copied/read back but carry a source-metadata pending obligation.

## Preserved credential migration archives

The candidate M07 extension snapshots only explicitly registered `native-credential-archives/<UUID>.handoff` and `<UUID>.holds` pairs. The first contains encrypted original values; the second retains the exact nonsecret hold inventory, including unresolved jobs, tables and assets. Metadata binds the pair to the import manifest, source schema/snapshot and reviewed destination namespace. Both files are private immutable inodes, pinned by independent clone or streaming copy; never hard links. A missing, changed, unsafe or unregistered reference cannot silently become a successful complete backup. This does not collect current Keychain values or export keys created/rotated after the original migration. Those credential/namespace obligations remain pending.
