# Maintenance staging recovery v1

This registry is separate from activation journals. Its only purposes are the outer `NextCRMMaintenance-<UUID>` temporary directory and `.nextcrm-pending-<UUID>` publication directory created by a maintenance operation. Completed backup/restore destinations, original databases, arbitrary folders with similar names, and activation-verification workspaces are never deletion targets. Recovery discovers entries only in an explicitly supplied private registry; it does not scan a user's selected folder.

`NativeDataMaintenanceRecovery(url:authorize:mutationFence:cancelled:checkpoint:)` creates or validates a dedicated 0700 registry. Existing registries require an owned marker and lock; initialization gaps are not silently adopted. Initialization also uses nonblocking flock: another process holding `.registry.lock` produces `recovery.busy` without waiting or changing its metadata. Cancellation is checked before and after acquisition, so an abandoned initializer cannot keep an application termination await blocked. A later invocation may retry after the owner releases the lock. `authorize` must check current session and the current user's administration rights. `mutationFence` must wrap its closure in the current database transaction and recheck those rights, so revocation and individual filesystem mutations are serialized. UI startup should run bounded `recover(after:limit:)` pages off the main thread and display pending items without presenting them as successfully cleaned.

Controller integration uses `.native-maintenance-recovery` under the current database root. This directory contains recovery bookkeeping, not CRM records or completed backup assets. `recoverStaging(after:limit:operation:)` is the bounded background API for root App startup/admin maintenance; root must not invoke a large sweep synchronously on the UI thread. Outcomes distinguish live, recovered, pending validation, and failed I/O, with an actual removed-directory count.

Integration points:

1. Begin a lease before creating work. The lease keeps an exclusive `flock` until destruction; each operation has an unpredictable UUID and its lock inode is persisted in every journal state and verified. Both another process and another independent open in the same process must skip a live lease. No PID/age inference is used.
2. Before each new Directory initializer, `plan(role:parentURL:name:)` records an absent path and parent device/inode. Immediately after creating the empty private directory, `attach(role:)` writes and fsyncs its immutable owner marker and records the new root's device/inode. A crash before the marker becomes durable is pending, not automatic deletion. The Controller does not start backend writes before attach returns.
3. Before publication rename, `beginPublication(destinationName:)` fsyncs intent. After the Controller transaction, namespace verification and successful rename, `didPublish()` records success. If termination occurs between these points, recovery observes the matching final inode and preserves it. It never deletes or walks the final destination. Ambiguous replacement remains pending.
4. Use lease `cleanup(role:)` for an unpublished registered directory, retaining its marker until all contents are removed. After the temp has been removed and the publication is published or removed, `finish()` removes the journal. Existing in-process rollback of a not-yet-successful publication remains the Controller's responsibility; offline recovery never performs that rollback. The extra ownership marker can remain in a completed artifact, but it alone never authorizes later deletion.

Each journal is append-only newline-delimited full state, at most 32 transitions and 256 KiB. Lines are at most 32 KiB, strictly parsed with duplicate-key rejection. Sequence and allowed transitions preserve the registered paths/identities. A torn trailing append is ignored because subsequent filesystem work cannot start before successful fsync; the next authorized write truncates only that incomplete suffix. Ownership markers are bounded 4 KiB. Durable state is written before creation/publication/deletion stages. An error keeps the last complete record for retry.

Recovery retains at most 100 result entries; it streams the private registry and selects a bounded lexicographic page. Directory traversal has bounded depth and stores one entry at a time. File contents are never loaded. Targets, ancestor paths, directory/file owners, private modes, registry marker, operation lock and inode identities are checked. Symbolic links/special files are refused. Owned regular hardlink pins are unlinked without altering the original inode. Every removal runs through fresh authorization and revalidates its root/parent; a cooperative publication cannot race with recovery because it holds the same lease.

Cancellation, authority loss, unexpected marker or inode, unreadable files, and I/O failures preserve a pending record. An empty root whose marker was removed during a previously recorded cleaning phase can be removed after identity verification. No unknown nonempty root without its marker is reclaimed. Same-user malicious changes to both private metadata and targets are outside this trust boundary, as with the application database; this is crash recovery, not a signed forensic provenance service. Actual power loss and filesystem hardware failure are not proven by process-crash tests. Tiny orphan lock files from interrupted initial registration and a registry interrupted before its own marker are retained; no folder-name-only sweep is used to guess ownership.

Cancellation or demotion can prevent further registry mutations. The existing in-process compensating cleanup may still remove only its freshly-created Directory objects, while the unfinished registry is retained for the next authorized recovery. If publication already committed, any subsequent ledger/cleanup failure preserves the completed artifact and reports cleanupPending; it never changes success into rollback. Recovery bookkeeping is not exported as restored CRM state and does not authorize deleting previously completed backups.
