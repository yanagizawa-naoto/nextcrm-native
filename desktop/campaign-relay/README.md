# キャンペーンの外部受信窓口

Macが休止・終了している間の配信停止と配信結果を、外部サーバーのSQLiteへ保存する任意のサービスです。Macアプリからこのプロセスを起動する処理はありません。

受信・永続化・署名検証・Swift通信・CRMへの同期反映・Keychain保存・日本語の接続設定画面・起動／復帰時の自動同期を実装しています。同期32件、設定サービス30件、自動実行21件、画面17件、専用のダミー接続情報による実Keychain操作4件を検証しました。実際のMac画面から保存し、再起動後の設定保持と自動同期もローカル受信窓口で確認済みです。外部HTTPS環境への公開と、キャンペーンの送信・予約・履歴・送信結果確認の画面は未実施です。

## 保存する情報

送信ID、配信停止トークン、送信サービスのメールID、配信結果の種類・受信日時を保存します。顧客名、メールアドレス、メール本文や受信した生の通知本文はデータベースへ保存しません。配信停止トークンと接続用の認証キーは秘密情報として扱います。

送信前にトークンを登録し、配信停止を受けた時点でSQLiteに確定してから日本語の受付画面を返します。Macが次に同期したとき、同じメールアドレスの対象者をまとめて停止します。再試行・再起動で同じトークンを登録しても新しい送信は発生しません。

配信結果はResendのSvix署名を確認してから保存します。ローカルの送信受付保存より先に届いた通知も保持し、メールIDが登録された時点で対応する送信に結び付けます。開封など同じ種類の繰り返しは最初の受信時刻を保持します。

## 実行と検証

追加パッケージは使いません。このワークスペースでは既存のNode v25.2.1と`node:sqlite`で検証しています。`DatabaseSync`と`timeout`オプションが必要です。この環境ではSQLiteの実験段階を示す警告が出ます。実際の外部運用は未検証です。[使用しているNode API](https://nodejs.org/download/release/v25.2.1/docs/api/sqlite.html)

```sh
zsh desktop/campaign-relay/test.sh
```

起動時の設定は次の環境変数で渡します。認証キーは32バイトの乱数をBase64URLの43文字で表した値です。設定値をGitへ保存しないでください。

| 変数 | 用途 |
| --- | --- |
| `NEXTCRM_RELAY_DATABASE` | このサービス専用のSQLiteファイルの絶対パス |
| `NEXTCRM_RELAY_AUTH_KEY` | ネイティブアプリと共有する接続用キー |
| `RESEND_WEBHOOK_SECRET` | Resendに設定したWebhookの署名キー |
| `NEXTCRM_RELAY_BASE_PATH` | 公開URLのパス部分。例 `/crm`。ルートなら空文字 |
| `PORT` | 内部HTTPポート。省略時8787 |

```sh
node desktop/campaign-relay/relay.cjs
```

待ち受け先は常に`127.0.0.1`です。外部サーバーで稼働させ、HTTPSのリバースプロキシから接続します。専用フォルダ・データベースの永続保存とバックアップが必要です。保存先フォルダが他の利用者から書き換え可能な場合、既存ファイルが他用途の場合、シンボリックリンクの場合は起動を拒否します。公開・契約・サーバー導入は自動では行いません。

## 公開ルート

`BASE_PATH`に続けて配置します。

- `GET /api/campaigns/unsubscribe?token=UUID`：配信停止を保存して日本語の受付画面を返します。
- `POST /api/campaigns/webhooks/resend`：元のHTTP本文と`svix-id`・`svix-timestamp`・`svix-signature`を検証します。時刻差は前後300秒までです。[Svixの署名仕様](https://docs.svix.com/receiving/verifying-payloads/how-manual)

配信停止とメールIDごとの配信結果は永続保存します。未照合のメールIDは最大10,000件まで保持し、古いという理由で自動削除しません。上限に達しても、対応する送信が登録済みの通知は処理できます。重複通知IDの検査用記録は30日後に順次削除しますが、最初の開封時刻などの配信結果は残ります。

## ネイティブアプリ用プロトコル v1

全リクエストに新しいUUIDの`X-NextCRM-Nonce`、整数秒の`X-NextCRM-Timestamp`、Base64の`X-NextCRM-Signature`を付けます。共有キーの生の値はHTTPへ送信しません。リクエストのHMAC-SHA256入力は、以下の文字列に生の本文バイトを続けたものです。`\n`は実際の改行です。

```text
nextcrm-relay-v1-request\nMETHOD\nRAW_PATH_AND_QUERY\nTIMESTAMP\nNONCE\nRAW_BODY
```

本文を再エンコードして署名し直してはいけません。時刻差は前後300秒、認証済みnonceの再利用は409です。通信再試行では新しいnonceを使い、業務上の送信ID・トークン・本文は維持します。

認証に成功したAPI応答の`X-NextCRM-Signature`は、以下の入力のHMAC-SHA256です。

```text
nextcrm-relay-v1-response\nREQUEST_NONCE\nHTTP_STATUS\nRAW_RESPONSE_BODY
```

応答署名を検証してからJSONを読み取り、`version`、`instanceId`、`clientId`を確認します。認証失敗応答に署名が付かない場合もあります。公開URLへのリダイレクトを自動追跡してはいけません。

| API | 本文またはクエリ |
| --- | --- |
| `GET /api/native-campaigns/v1/health` | 受信窓口ID・接続済みCRM ID・履歴の末尾を取得 |
| `POST /api/native-campaigns/v1/bind` | `{"clientId":"UUID"}`。初回のみ接続。別のCRMへの付け替えは409 |
| `POST /api/native-campaigns/v1/registrations` | `{"clientId":"UUID","registrations":[{"sendId":"UUID","token":"UUID","providerId":"任意"}]}`。最大100件。全件を一つのトランザクションで登録 |
| `GET /api/native-campaigns/v1/events?clientId=UUID&after=0` | 最大100件を番号順で取得。`cursor`と`hasMore`を返す |

送信IDとトークンは登録後に変更できません。メールIDは受付後に追記できますが、他の送信への付け替えはできません。履歴番号には欠番があり得ます。番号が増加すること、現在位置が受信窓口の履歴末尾を超えないことを検証します。バックアップ復元などで履歴が巻き戻った場合は、送信を止めて状態を確認し、自動的に同期位置をリセットしてはいけません。

Mac側では、受信イベントの反映と同期位置の保存を同じSQLiteトランザクションで行う必要があります。配信停止を全ページ反映し、送信対象・権限・実行権を再確認してからメールを送ります。通信処理は`CampaignRelayClient.swift`で実装し、応答署名・受信窓口ID・ページ順序の検証と最大1 MiBのストリーム読み込みを行います。署名・不正な応答の検査と、実際のローカルHTTP受信窓口への接続を含む34件のチェックを通過しています。`CampaignRelaySync.swift`ではCRMへの反映と同期位置の保存を同じトランザクションで行い、登録済みの受信窓口への接続を維持します。206件のページ分割、途中失敗後の再開、同時同期の競合、送信直前の配信停止もローカル検証済みです。`CampaignRuntime.swift`と`CRMApp.swift`が起動・復帰・設定保存・送信受付後に保存済みジョブを起動します。同期要求はまとめ、通信失敗時は時刻を保存して再試行します。処理がなければ定期タイマーは動きません。キャンペーンの送信操作・履歴・送信結果確認の画面が次の実装対象です。

## Mac側の接続設定

開発版の「NextCRM Native」メニューから「キャンペーンの受信窓口…」を開きます。管理者が公開URL、メールのアプリ名、接続キーを入力し、「接続を確認して保存」を選択します。差出人とResend APIキーは、別の「メール送信の設定…」で管理します。

接続確認では、管理用APIに加えて実際の公開経路 `GET /api/campaigns/unsubscribe?check=ready&clientId=UUID` を使用します。この操作にも通常のリクエスト・応答署名を適用し、登録済みCRM IDと受信窓口IDを照合します。配信停止トークンを渡さず、顧客の停止状態やイベント履歴は変更しません。公開経路がプロキシ等で遮断されている場合は保存・送信を中止します。

接続キーはKeychainへURL・接続IDとまとめて保存します。画面に保存済みのキーは表示しません。同じ接続先の名称を変える場合はキーを空欄にすると保持できます。接続確認は途中で中止できます。キーを削除しても既存の受信窓口IDと同期位置は残るため、再接続で履歴を勝手にリセットしません。

検証用アプリだけは専用データフォルダと固定のダミーキーを使い、HTTP通信先をMac内に制限します。検証用の公開設定にはキーを保存せず、実運用のKeychainへアクセスしません。検証時に手動起動するローカル受信サーバーは、Macアプリが常駐させるプロセスではありません。
