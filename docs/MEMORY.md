# メモリ測定

READMEの主表示は10進のMBです。**1 MB = 1,000,000バイト**、参考として併記する **1 MiB = 1,048,576バイト**です。

## 同条件に近づけた比較（2026年11月26日・日本時間）

同じMacで、同じ合成データ10,000件の営業対象一覧を待機表示しました。各実装・表示状態につき3回独立して起動し、各起動で5点を測定しています。代表値は「5点の中央値」を3回分集めた中央値です。

| 状態 | 構成 | 代表値（バイト） | MB | MiB（参考） |
| --- | --- | ---: | ---: | ---: |
| バックグラウンド | 保存済み軽量化Web版 | 560,240,536 | 560.24 | 534.29 |
| バックグラウンド | Native版 | 68,470,848 | 68.47 | 65.30 |
| 前面表示 | 保存済み軽量化Web版 | 655,890,088 | 655.89 | 625.51 |
| 前面表示 | Native版 | 64,505,872 | 64.51 | 61.52 |

今回の保存済みWeb環境に対する参考削減率は、バックグラウンド **87.8%**、前面表示 **90.2%** です。式は `(1 - Nativeの代表バイト数 / Webの代表バイト数) × 100` で、丸める前の値から計算しています。

**Web版には、Inngestが内部送信の認証キーを拒否するエラーが残っています。** 設定した検証用イベントキーの受け付けと一覧・検索・詳細の動作は確認しましたが、バックグラウンドジョブが完全に正常なWeb版との比較ではありません。このため削減率は参考値として掲載しています。測ったのは保存済みの軽量化Webデスクトップ環境であり、上流の未改変版や初期のVM構成ではありません。

| --- | --- | ---: | ---: | ---: | ---: |
| バックグラウンド | Web | 560.24 MB | 579.90 MB | 556.36 MB | 556.29–580.08 MB |
| バックグラウンド | Native | 67.85 MB | 68.47 MB | 68.52 MB | 67.82–68.57 MB |

## 揃えた条件

- **機器：** Apple M2、物理メモリ17,179,869,184バイト（約17.2 GB / 16 GiB）、macOS 26.6.2。同じディスプレイ、表示倍率2倍。
- **データ：** 合成した営業対象10,000件。IDを含む36のスカラー項目と所有者情報を両実装で一致させました。NativeはSQLite、WebはPostgreSQLです。測定後にも対象・所有者の正規化SHA-256が一致し、Nativeの107テーブルの件数が変わらないことを確認しました。実データや実サービスの認証情報は使っていません。
- **実装：** Nativeは最終453 Swiftソースと同じ本体ソースを使う最適化済み隔離検証ビルド。Webは保存済み軽量化版のサーバーJavaScriptを変更せず、検証用ホストから起動しました。WebサーバーのビルドIDは `rDrHRWu2i6x1njBSDMJEw` です。
- **画面：** 内容領域は両方とも1280×760ポイント。タイトルバーを含む外枠はNative 1280×788、Web 1280×792ポイントです。WebKitの描画準備を完了させるため、両方とも全画面化して通常表示へ戻しました。
- **バックグラウンド：** 準備後にmacOSの「隠す」を実行。測定時の表示状態検査で非アクティブ・非前面・非表示を確認しました。ウィンドウを閉じた状態ではありません。
- **前面表示：** 各測定の前後で、アクティブ・非表示ではないこと、最前面PIDの一致、対象ウィンドウが画面上にあることと寸法を確認しました。
- **採取：** 画面準備後30秒以上待機し、開始時刻の間隔10秒を目標に5点採取。起動間では専用アプリ・サービス群をすべて終了してから再起動しました。測定中にビルド・テストは実行していません。

1ページの表示件数は製品の既定値を保持し、Native 100件、Web 10件です。**10,000件を一度に描画した実験ではありません。** 実装のページング・保存方式が異なるまま、同じ保存データを一覧で扱う場合を比べています。

## 集計に含めたプロセス

macOSの `footprint` に、専用プロセスツリーとアプリへの帰属を検査したresource coalition内の関連プロセスをまとめて渡しました。**一度の呼び出しが返すphysical footprintの合計**を使い、個別PIDの値を単純加算していません。RSSとは異なる指標です。採取前後で対象プロセスの帰属・構成を確認しています。

- **Native（採用点は各3プロセス）：** アプリ本体、SafariPlatformSupport.Helper、ThemeWidgetControlViewService。
- **Web（採用点は各15プロセス）：** アプリ本体、WebKitのWebContent・GPU・Networking、Node.js、Inngest、PostgreSQL本体と子プロセス、関連するテーマ表示・音声サンドボックスのヘルパー。

共有のWindowServerや、無関係なOSプロセス・ユーザーアプリは除外しています。そのためMac全体の増分メモリを直接表す値ではありません。

## 試行の採用・再試行

前面の採用順は **Native → Web → Web → Native → Native → Web**。6回の起動、全30点が再試行なしで採用されました。

バックグラウンドの最終採用順は **Web → Web → Native → Native → Web → Native** です。当初は検索・詳細からの復帰も計画しましたが、元の質問に対応する10,000件の一覧を主比較とし、ほかの場面は探索的な観測として扱いました。途中でプロセス帰属の検査失敗を受けて再試行規則も変更しており、事前計画を一切変更せずに完遂した実験ではありません。

最終的な規則は、両実装とも「帰属検査が1点でも失敗したら、その場面の5点をすべて無効とし、同じ画面で30秒待って5点すべてを再測定」です。メモリ値が小さい点だけを残すことはしていません。最初のWeb起動では一覧の5点がすべて有効だったため、後続の検索場面が失敗しても一覧は保持しました。別のWeb一覧ではPostgreSQLの一時的な子プロセスにより構成検査が失敗し、その場面全体を取り直しました。

最初のNative予備試行は、Web側で必要になった「全画面化して戻す」準備を行っていなかったため、主比較から外して同じ準備を行った独立起動に置き換えました。除外理由は表示準備の違いであり、メモリ値の大小ではありません。無効・予備試行の生記録はローカルに保持していますが、公開JSONは採用した主比較60点のみです。

## この結果から断定できないこと

- 前面とバックグラウンドは別時刻の実験です。Nativeの前面値が小さいことを「前面化するとメモリが減る」という因果関係として読めません。
- OSキャッシュは消去せず、他のユーザーアプリも閉じていません。起動し直していても、OSキャッシュまで完全に冷えた状態ではありません。
- 3回の起動・短時間の一覧待機の結果です。通常利用の全場面で100 MB未満になる保証や、長時間運用・スクロール・編集・取り込み・添付・外部連携のピーク測定ではありません。
- 公開データは採用点を検算するための抜粋です。各点のSHA-256はローカルの生の `footprint` JSONを識別するためのもので、生記録を独立に検証できる証明ではありません。個人のパス、実行環境の認証設定、メール通知情報、生のプロセス情報は公開していません。
